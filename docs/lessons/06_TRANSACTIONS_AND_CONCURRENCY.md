# 第8—9课：一起成功、一起撤销，和同时修改

[回目录](../LEARNING_GUIDE.md) · [上一课](05_LOGIN_AND_OWNERSHIP.md) · [下一课](07_TESTS_AND_INDEXES.md)

**今天的目标：** 用实际例子理解事务、唯一键、锁和版本号分别干什么。

## 1. 加到一半失败了

你要把论文1、论文2、论文999999一起加进新列表。前两篇存在，最后一篇不存在。

我们决定：这批操作要么全部完成，要么一篇都不加。这个边界叫**事务（transaction）**。

- **BEGIN**：开始这一包操作。
- **COMMIT**：确认这包操作保存成功。
- **ROLLBACK**：出了问题，把这包尚未提交的修改撤销。

不是撤销整个数据库历史，也不会删除你之前已经成功加入的论文。

## 2. 对照真实代码

打开 [`navigator/db.py`](../../navigator/db.py)，找 transaction：

```python
conn.begin()
try:
    yield conn
    conn.commit()
except BaseException:
    conn.rollback()
    raise
```

- `conn` 是数据库连接。
- `try` 表示尝试执行；`except` 表示出异常后走另一条路。
- `yield` 在这个带 contextmanager 的函数里，把中间位置交给使用 `with transaction():` 的业务代码。
- 中间代码成功返回，才 commit。
- 中间出错，就 rollback；`raise` 把错误继续交给上层处理。

初次阅读不用独立实现 contextmanager，只需要识别“中间放业务，外面包提交和撤销”的结构。

在 [`navigator/services.py`](../../navigator/services.py) 找 batch_add：它在 `with transaction():` 里面核对列表、逐篇检查并插入论文。

## 3. 亲眼看一次回滚

1. 新建一个空列表，比如 `回滚练习`。
2. 在 Add several papers 中输入 `1, 999999`。
3. 点击 Add papers。
4. 应该看到错误说明。
5. 回到该列表，它应该仍为空，论文1没有留下。
6. 再输入 `1, 2`，这次应该看到两篇。

这个练习验证了业务承诺，不需要先相信术语。

注意：这里演示的是数据插入的事务。MySQL 的建表等 DDL 语句通常会隐式提交，所以不能推断“整个 schema 初始化失败也一定自动撤销”。

## 4. 重复点击怎么办？

再次输入 `1, 2, 2`，不应该变成五条记录。

这里有两层去重：

- 程序先处理本次输入的重复编号。
- 数据库的 `(list_id,paper_id)` 主键保证最终不能存同一对两次。

`ON DUPLICATE KEY UPDATE` 在这里把已经存在的成员当作不需要改动。这不是忽略所有错误：不存在的论文等错误仍会失败。

这种重复请求不改变最终成员结果的性质，叫**幂等性（idempotency）**。先把它读成“多做一次，不多加一份”。

## 5. 同时来的两个人

**并发（concurrency）**指多个操作在时间上重叠。两个请求可能都先查“还没有论文1”，然后都想插入。

只说“我用了事务”不够。事务的原子性回答“这一包成功还是失败”，不自动保证两个请求不会争同一条数据。

我们的列表操作先用 `SELECT ... FOR UPDATE` 锁住那一份列表的行。可以暂时理解为：同一个列表先由一个请求处理，其他要获得该行写锁的请求等它提交或回滚。不是把全世界的所有列表都锁住。

即使有锁，唯一键仍然保留，作为数据正确性的最后一道规则。

两个请求同时加入同样两篇的测试结果是：一个新增2篇，另一个新增0篇，最后只有2篇。

## 6. 为什么阅读进度还需要版本号？

假设一篇论文现在是：

```text
status = want
version = 1
```

两个页面都读到了这份旧信息。

- 页面A提交“在读，基于版本1”。保存后变成版本2。
- 页面B随后提交“已读，基于版本1”。服务器发现现在已经是版本2，拒绝这次旧版本修改。

代码的关键条件是：

```sql
UPDATE reading_states
SET status=%s, version=version+1
WHERE user_id=%s AND paper_id=%s AND version=%s
```

最后的 version 条件要求“你看到的版本还是现在这一版”。零行被更新，表示条件不成立；应用返回409，让用户刷新。

这叫**乐观并发控制**：平时不长期占着锁等待用户读页面，提交时核对版本。

## 7. 两标签页练习

1. 用同一个账户打开论文1，先保存一次状态。
2. 在两个标签页都重新打开论文1，让它们读到相同版本。
3. A选 Reading 并保存。
4. 不刷新B，在B里选 Finished 并保存。
5. B应该收到409冲突提示。
6. 刷新B，确认当前状态，再决定是否修改。

即使A选择了与原来相同的状态，当前实现也会推进版本；这不影响练习。

## 8. 四个工具分别回答什么？

|工具|它主要回答的问题|
|---|---|
|事务|一包操作失败后，是否留下半包结果？|
|唯一键|是否出现不允许的重复数据？|
|行锁|同时写同一个列表时，谁先处理？|
|版本号|用户是否用旧页面覆盖了新修改？|

## 小任务

在原本已有论文3的列表中，批量加入 `1, 999999` 失败后，论文3会消失吗？锁会在用户关闭整个网站后才释放吗？

<details><summary>参考答案</summary>

不会。事务回滚撤销本次未提交的改动，保留先前已提交的论文3。这个业务事务中的行锁通常在提交或回滚时释放，不是等用户关闭网站。

</details>

**过关标准：** 不看代码，用一个失败例子解释事务，用两个请求解释锁或版本号。
