# 第10—11课：证明它没坏，也弄清它为什么快

[回目录](../LEARNING_GUIDE.md) · [上一课](06_TRANSACTIONS_AND_CONCURRENCY.md) · [下一课](08_REVIEW_AND_INTERVIEW.md)

**今天的目标：** 读懂一个测试，并理解性能数字的边界。

## 1. 测试像一份检查作业的答案纸

“我点过一次，好像没问题”证据不够。程序还要面对错误密码、不存在的论文、别人的列表、两个同时来的请求。

**自动测试**就是把这些输入和预期结果写成程序，每次修改后可以重复检查。

打开 [`tests/test_application.py`](../../tests/test_application.py)，找到 test_search_filters_and_pagination。你会看到：

```python
assert client.get("/papers?page=0").status_code == 400
```

逐块读：

- client：测试用的模拟访问工具，可以先理解为没有屏幕的浏览器助手。
- `.get(...)`：发一个 GET 请求。
- page=0：故意给一个不允许的页码。
- status_code：响应状态编号。
- assert：断言，意思是“这里必须符合我的预期”。不符合就让测试失败。
- 400：服务器认为输入不正确。

这不是打开真正的浏览器点按钮。测试客户端直接调用 Flask，但后面的数据查询和写入使用**真实 MySQL**。

## 2. 常见状态编号

|编号|通俗解释|项目例子|
|---|---|---|
|200|成功返回|打开论文页|
|302|请去另一个地址|未登录时跳到登录页|
|400|输入不合要求|页码0或缺少CSRF token|
|401|身份验证未通过|密码错误|
|404|这里没有可访问的内容|不存在或不属于你的列表|
|405|请求方式不允许|用GET请求删除接口|
|409|与现有数据或版本冲突|重复评价、旧版本保存|
|429|请求过于频繁|短时间大量登录尝试|
|503|数据库暂时不可用或忙|连接失败、锁等待等|

编号不是万能原因说明，仍要结合页面提示和日志。

## 3. 三段式读测试

一个测试通常分成：

1. **准备**：创建账户和列表。
2. **操作**：发送一个请求。
3. **核对**：检查返回值，以及数据库最终是否真的变了。

例如只检查“页面显示添加成功”还不够，要查数据库有没有重复；只检查“返回了错误”也不够，要查前面已经插入的内容是否回滚。

`conftest.py` 中的 fixture 是测试准备工具，会安排干净的数据和账户。这里 fixture 也用于指样例数据；结合上下文理解即可。

## 4. 怎样运行？

**Docker 路线：** 在项目根目录运行：

```bash
docker compose --profile test run --build --rm test
```

它会启动单独的测试数据库，不使用网页里的个人阅读数据。`--profile test` 启用测试配置，`--rm` 在测试容器退出后移除该容器。

**原生路线：** 先确保本地已创建专用的 `navigator_test` 数据库，而且项目账户有权访问它。本次实现时已经为这台机器准备过。

```bash
source .venv/bin/activate
python -m pytest --cov=navigator --cov-report=term-missing -q
```

- pytest：运行测试的工具。
- `--cov=navigator`：统计测试执行到了 navigator 中哪些 Python 语句。
- `--cov-report=term-missing`：在终端显示哪些语句未覆盖。
- `-q`：少说一些运行过程信息。

测试会删除 **navigator_test 中的样例行**，因此绝不能往这个专用测试库里放想保留的资料。它会拒绝换成其他库名运行。

当前提交的本地记录是 `29 passed`，报告语句覆盖率98%。以后新增测试，数量可能变多。测试会花时间，看到终端暂时没有返回提示符，不代表一定卡死。

## 5. 覆盖率98%是不是“98%正确”？

不是。它只是说这轮测试执行到了大约98%的被统计 Python 语句。执行过不代表检查到了所有逻辑错误，也不代表样式、每种浏览器或所有并发顺序都验过。

所以项目还保留“没有截图视觉验收”等明确边界，不能把数字理解为百分之百安全或完整。

## 6. 索引：像书末目录

没有合适目录时，找2026年的文章可能要检查很多条记录。有按年份安排的索引，可以更快定位符合年份的范围。

数据库中的**索引**是辅助查找的数据结构，不是另一份网页阅读清单。它要占空间，写入时也需要维护，所以不是越多越好。

本项目比较的索引是：

```sql
(publication_year, paper_id)
```

先按年份组织，再按编号组织。这个实验要找2026年、编号最大的20篇论文，再关联作者，很适合讨论这条访问路径。

## 7. 两种“解释查询”

- `EXPLAIN`：看数据库准备怎么执行，以及它估计要付出多少代价。
- `EXPLAIN ANALYZE`：实际运行并观察执行步骤、耗时与行数。

“估计成本 cost”像系统自己计算的评分，不是毫秒。就像地图估计路线难度和你真的走了几分钟，是两个不同量。

打开 [`docs/evidence/benchmark.json`](../evidence/benchmark.json)。JSON 是一种保存结构化数据的文字格式，外观像 Python 字典，但不是同一种语法。先只找这些字段：

|字段|意思|
|---|---|
|paper_rows|实验放了多少篇合成论文|
|query|运行哪条SQL|
|parameters|这次填入什么参数|
|before / after|加索引前 / 后|
|milliseconds|每一轮测到多少毫秒|
|median_ms|把耗时排序后取中间位置的中位数|
|explain_analyze|实际执行步骤|

## 8. 真实记录怎么读？

这次实验有30,000篇合成论文、200位合成作者、60,000条作者关系。不要和网页里的16篇样例论文混为一谈；实验在专用测试库的 bench_* 表里。

|条件|20轮的中位耗时|取到20篇目标论文前观察到的论文扫描量|
|---|---|---|
|加年份索引前|约0.303毫秒|1103行|
|加年份索引后|约0.200毫秒|20行|

数据库已有主键索引，所以前者也不是“完全没有索引”。它先倒着扫主键，再筛年份；后者通过年份索引定位。

最后返回40行，因为20篇论文各有两位合成作者。程序核对了索引前后的结果完全一致。

这次每个条件先预热3轮，再测20轮。**预热**可以先理解为让数据进入缓存，减少第一次准备的影响。实验是本机、热缓存、单个客户请求；亚毫秒数字容易受到噪声影响。不能据此说“真实网站所有查询都快了这么多”。

## 9. 先读结果，再决定复现实验

[`scripts/benchmark.py`](../../scripts/benchmark.py) 会在专用测试库建立 bench_* 表。它拒绝覆盖已经存在的实验。第一次学习先读已有 JSON，不需要删除旧实验。

确实有全新的专用测试库时，按 README 的 Database experiment 部分运行。若看到已有表的提示，停下保留数据，不要随意删除表来消除报错。

## 小任务

为什么“返回40行”不代表找到了40篇不同论文？为什么98%覆盖率不等于98%正确？

<details><summary>参考答案</summary>

实验先选20篇论文，再把每篇的两位作者展开成两行，所以是40个论文—作者组合。覆盖率只统计代码是否被执行到，不衡量所有结果是否正确。
