# 第7课：你是谁，这个书单又是谁的？

[回目录](../LEARNING_GUIDE.md) · [上一课](04_HTML_AND_FIRST_EDIT.md) · [下一课](06_TRANSACTIONS_AND_CONCURRENCY.md)

**今天的目标：** 分清登录和权限。它们相关，但不是一件事。

## 1. 两道问题

图书馆管理员先问：“你是谁？”核对身份后再问：“你能改这个书单吗？”

- **认证 Authentication**：确认你是哪个账户。
- **授权 Authorization**：决定这个账户能做什么。

登录成功不意味着能修改所有人的列表。

## 2. 密码不能明文存

打开 [`navigator/auth.py`](../../navigator/auth.py)，找 `generate_password_hash`。注册时，代码用标准库里的 scrypt 算法把密码变成用于验证的摘要，这叫**密码哈希**。

它不是把密码藏进一段能直接解密回原文的字符串。验证时，用库提供的 check_password_hash 检查用户这次输入是否匹配已保存的摘要。

摘要里包含算法、参数和随机盐等信息；盐可以先理解为每次计算加入的随机材料。因此两个账户使用同样密码，也不应简单得到相同的存储字符串。不要自己发明密码算法。

现在不用学习 scrypt 的数学，只要能说：“数据库没有直接存下我的原始密码。”

## 3. 为什么不用每点一下就输入密码？

登录后，服务器给浏览器一个随机的会话 token，可以暂时理解为“本次登录的通行证”。Cookie 是浏览器保存并按规则随请求带回的小段数据。

我们的流程：

```text
你输入邮箱和密码
  → 核对密码
  → 生成随机登录 token
  → 数据库保存 token 的哈希摘要与到期时间
  → 浏览器保存包含 token 的签名 Cookie
  → 下次请求核对这张通行证是否仍有效
```

签名用于检查 Cookie 是否被篡改，不等于把内容加密。这里不把密码放进 Cookie。

在 auth.py 中依次找：

|函数|你现在可以这样理解|
|---|---|
|register|登记新账户|
|login|检查邮箱与密码|
|sign_in|发新的登录通行证|
|load_user|每次请求确认通行证对应谁|
|logout / revoke_session|让旧通行证失效|

数据库中的会话最长12小时。退出会删掉对应记录，所以复制的旧 Cookie 也不能继续当作有效登录使用。这是自动测试检查过的行为。

## 4. 真正决定列表归属的代码

打开 [`navigator/services.py`](../../navigator/services.py)，找 owned_list：

```python
row = query(
    "SELECT * FROM reading_lists WHERE list_id=%s AND owner_id=%s" +
    (" FOR UPDATE" if lock else ""),
    (list_id, user_id), one=True
)
```

先只看条件：

- list_id 必须是你想访问的列表。
- owner_id 必须是当前登录用户。
- `AND` 表示两个条件都要成立。

user_id 来自服务器核对过的会话，不相信表单自己宣称“我是用户1”。找不到满足两个条件的列表，就返回404。

`FOR UPDATE` 是后面一课会讲的锁，这一课可以先跳过。

## 5. 隐藏按钮为什么还不够？

别人可能自己构造一个请求，完全不点击你的页面按钮。所以每个后端写操作也必须检查身份和归属。

就像把“员工入口”的牌子藏起来，并不能代替门锁。网站必须在处理请求时再次核对。

## 6. CSRF 是什么？

先不背缩写。想象你已经登录，一个陌生网页试图借你的登录状态偷偷提交表单。

本项目的表单会带一个服务器验证的 CSRF token。Flask-WTF 检查它，缺少或不匹配就拒绝。登录 token 和 CSRF token 用途不同：一个记住登录身份，一个帮助核对表单提交。

**HttpOnly** 限制浏览器脚本读取 Cookie；**SameSite=Lax** 限制某些跨站请求携带 Cookie；**Secure** 要求 Cookie 通过 HTTPS 发送。它们各自解决一部分问题，不是装上一个开关就保证整个网站安全。

本地 HTTP 演示的 Secure 配置与公网 HTTPS 不同，详见 README。现在先不要修改安全设置。

## 7. 手动检查两个账户

1. 在普通窗口用账户A创建一个列表，记下它的地址，例如 `/lists/某个编号`。
2. 用另一个隔离的浏览器会话登录账户B，例如另一个浏览器或无痕窗口。普通的第二个标签页通常仍共享A的 Cookie，不能当作B。
3. 用B打开A的列表地址。
4. 预期看到404；A回去仍然能正常打开。

使用你自己的本地练习账户即可。不要操作别人真实的数据。

## 小任务

为什么知道列表编号不能证明你拥有列表？外键能解决这个问题吗？

<details><summary>参考答案</summary>

编号只是地址，知道地址不等于获得修改权。外键检查引用的记录是否存在；当前请求的用户是否有权读写，需要后端做授权检查。

</details>

**过关标准：** 你能清楚区分“谁登录了”和“谁拥有这个列表”。
