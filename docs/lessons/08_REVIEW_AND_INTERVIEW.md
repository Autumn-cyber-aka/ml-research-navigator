[回目录](../LEARNING_GUIDE.md) · [上一课](07_TESTS_AND_INDEXES.md)

**今天的目标：** 用自己的话讲清项目，不背一串听起来厉害的名词。

## 1. 把一次操作画成故事

拿“把论文1加入我的列表”来说：

```text
浏览器表单：我想加入论文1
  ↓
CSRF检查：这次表单提交是否合规？
  ↓
登录会话：当前请求是哪个账户？
  ↓
routes.py：读出并检查列表编号等输入
  ↓
services.py：这个列表属于该账户吗？
  ↓
数据库事务：锁住列表，检查论文，保存成员关系
  ↓
提交成功：返回跳转，页面显示结果
```

如果论文不存在，中间回滚；如果列表属于别人，不允许修改；如果同一成员已经存在，保留一份。

“后端”指这里负责请求处理和业务操作的服务程序；“前端”指用户在浏览器里使用的页面。我们的前端主要由服务器生成 HTML，不必有 React 才叫前端。

## 2. 阅读源码的最终顺序

第一次读完教程后，再按这个顺序完整读文件：

1. `sql/fixture.sql`：先知道数据长什么样。
2. `sql/schema.sql`：看字段、键和规则。
3. `navigator/templates/papers.html`：看搜索输入与结果区域。
4. `navigator/routes.py` 的 papers、paper_detail：读一条查询路线。
5. `navigator/db.py`：理解查询执行和连接。
6. `navigator/auth.py`：理解当前用户怎么得到。
7. `navigator/services.py`：理解业务事务、权限和版本。
8. `navigator/routes.py` 的列表与讨论操作：把前面工具串起来。
9. `tests/test_application.py`、`test_concurrency.py`：看如何证明行为。
10. `scripts/benchmark.py`：读性能实验。
11. `navigator/__init__.py`：回头理解应用如何组装、配置与处理错误。
12. Dockerfile、compose.yaml、GitHub workflow：最后看运行和自动检查环境。

一次只追一个函数的调用路线。不要因为一个文件几百行，就以为必须从第一行连续背到最后一行。

## 3. 三个循序渐进的小改动

### 练习A：改界面文字

按第6课改一句标题，保存并看到效果，再改回。验收：git diff 能解释每个改动。

### 练习B：补一个错误输入测试

在 `tests/test_application.py` 最后新增：

```python
def test_blank_review_is_rejected(app, alice):
    response = post(alice, "/papers/1/reviews", {"rating": 3, "body": "   "})
    assert response.status_code == 400
    assert scalar(app, "SELECT COUNT(*) FROM reviews") == 0
```

这里 app、alice、post、scalar 都是现有测试文件已经使用的准备工具或辅助函数，不要粘到其他随机文件。

它发送只含空格的评论，检查输入被拒绝，而且没有留下数据库记录。先解释每行，再按第10课运行测试。新增测试通过后，原本38个测试应变为39个（前提是没有其他人同时修改测试）。这是留给你亲手完成的练习，目前仓库没有替你加上它。

### 练习C：找一条限制，提出改进

例如深分页较慢、没有忘记密码、只有一层回复。只选一个：说清问题何时出现、想怎么改、会新增什么测试。先提出方案，不要求马上做一个大系统。

## 4. 五个常见误解

|误解|更准确的说法|
|---|---|
|GitHub 仓库就是公网网站|仓库保存代码；后端仍需要服务器和数据库运行|
|主键编号就是总人数|编号可能有空缺，数量要统计|
|用了事务就没有并发问题|还要看唯一键、锁、隔离与版本条件|
|没有显示删除按钮就安全|后端每次请求仍要检查权限|
|ML 项目表示训练了模型|这里 ML 是论文领域，项目没有训练模型|

## 5. 面试先讲30秒，再讲细节

练习时可以用下面这个结构，但要换成自己的话：

> 这是一个用 Flask 和 MySQL 做的论文管理应用。用户可以找论文、建立私人列表并记录阅读进度。我重点研究的是数据关系、权限和事务。例如批量加入论文时，只要有一个编号不存在，就回滚整批；同一列表的并发写入用行锁和唯一键处理。测试和性能实验都有原始记录。初始实现由 AI 辅助，我能具体说明自己审阅、修改和验证过的部分。

如果你还不能解释某一部分，就不要把“我重点研究”当成已完成事实。先做练习、记贡献，再用过去式讲经历。

针对 Snowflake、Databricks 等数据平台相关岗位，这个项目可以用来讨论关系建模、SQL、正确性、并发和性能；这不是官方面试题纲，也不能替代算法和系统基础学习。没有实现的分布式计算、分片和模型训练，不要写成已有能力。

## 6. 不看答案的自测

1. 一篇论文的两位作者为什么不存成一个逗号分隔字符串？
2. users 和 authors 为什么分开？
3. Reading lists 和 reading_states 为什么分开？
4. query 中的 `%s` 是做什么的？
5. 用户B猜到A的列表编号为什么仍改不了？
6. 批量加入到一半失败，哪些记录会撤销？
7. 两个请求都先查到“不存在”，为什么还需要唯一键？
8. version=1 的旧页面遇到数据库版本2时会怎样？
9. EXPLAIN 的 cost 为什么不能当作毫秒？
10. 测试通过后，还不能声称什么？

<details><summary>参考答案：先自己回答再展开</summary>

1. 需要可靠地表示身份、顺序和多对多关系，便于查询与约束。
2. 作者是论文元数据中的研究者，用户是注册使用软件的账户。不能把虚构作者或导入的审稿人自动当成真实用户。
3. 一份是分组关系，一份是每人每篇的进度，移出清单不应清空进度。
4. 它是 SQL 参数占位符，值交给数据库驱动处理。
5. 后端用会话身份检查 owner_id，不相信客户端声称的 user_id。
6. 撤销当前事务尚未提交的改动，不撤销之前已提交的数据。
7. 并发情况下两个检查可能都通过，数据库唯一规则仍需保证最终不重复。
8. 更新条件不匹配，返回409，让用户刷新再决定。
9. cost 是优化器模型的估计单位，实际耗时需要测量。
10. 不能声称所有浏览器都验过、生产负载表现优秀、完全安全、拥有真实活跃用户，或自己已独立掌握所有代码。

</details>
