# 第13—15课：把自己的图书馆变成小社区

先学完第7—10课。你已经认识用户、表、权限和测试。这三课用同样的积木，搭出新功能。

## 第13课：点赞像贴一颗小星星

小红写了一段读书感想，小明觉得有帮助，就贴一颗星。小明点十次，也只能算一颗；小明可以收回自己的星，不能拿走别人的星。作者不能给自己贴星。

本项目可以给**论文评论、讨论帖、公开书单**点赞。论文的1—5分评分是另一件事：评分评价论文，点赞表示这条内容有帮助，两者没有混在一起。

### 先亲手试一次

1. 注册账号甲，打开一篇论文，写一条评论。记住这篇论文。
2. 退出账号甲，注册账号乙，再打开同一篇论文。
3. 在甲的评论下面点 `Helpful`（有帮助）。数量应增加1，按钮变成取消。
4. 取消点赞，数量应减1。再登录甲，不能给自己的评论点赞。
5. 用同样方法试讨论帖。先有真实内容才有点赞，程序不会替你造热闹。

### 如果从空白开始写，按这个顺序做

**第一步：画表。** 打开 [`sql/migrations/002_community.sql`](../../sql/migrations/002_community.sql)。`review_votes` 就是评论星星登记册：

|review_id 评论编号|user_id 用户编号|意思|
|---|---|---|
|17|8|8号用户给17号评论点了赞|
|17|9|9号用户也给17号评论点了赞|

`PRIMARY KEY (review_id, user_id)` 是两列合起来不能重复。数据库会阻止“8号用户给17号评论留下两颗星”。另外两本登记册叫 `post_votes` 和 `list_votes`。

**第二步：写收表单的人。** 在 [`navigator/community.py`](../../navigator/community.py) 找 `vote`。它接收 `like`（点赞）或 `unlike`（取消），检查登录，再找目标记录。私有书单不能点赞。`FOR UPDATE` 是先拿到这条记录的钥匙再处理，和第9课的锁是同一个概念。

**第三步：让重复请求也有正确结果。** 网络可能把同一个请求重发两次。代码使用 `ON DUPLICATE KEY UPDATE`，重复点赞后仍然只有一行。这个性质叫“幂等”：重复做同一件事，结果不多出一份。

**第四步：显示数量。** `attach_votes` 用 `COUNT(*)` 数星星。没有另外存一个随时可能忘记更新的计数器。页面按钮在 [`macros.html`](../../navigator/templates/macros.html) 的 `vote_button`，里面带着第7课认识的 CSRF 票据。

**第五步：检查。** 打开 [`tests/test_community.py`](../../tests/test_community.py)。找重复点赞和同时点赞的测试。它们不仅看按钮，还确认数据库最终只有一行。自己把“重复点赞应该变成两行”写在纸上，想想为什么这是错误答案。

### 公开书单像把自己的推荐书单贴到公告栏

原来的书单默认是私人抽屉。现在主人可以主动点 `Publish this list` 把书单贴出去。打开自己的书单详情即可看到分享区域。公开后可从侧栏 `Community lists`（社区书单）找到，访客能看论文清单，其他登录用户能点赞。

公开的内容包括书单标题、说明、作者显示名和选了哪些论文。**个人阅读进度仍然不公开。** 别人在公开页面看不到“你今天读到哪里”。不要把私人笔记写进准备公开的书单说明。

从零实现的顺序：先给 `reading_lists` 加 `is_public`（是否公开）列，默认是假；再写只允许主人修改的发布操作；然后写只查询公开书单的入口；最后测试取消公开后旧链接返回404。旧页面用 `version` 检查，避免覆盖更新。

练习：甲公开书单，乙打开并点赞；甲取消公开，乙刷新旧链接。预期：404。404表示这个入口现在找不到可公开的内容，不是数据被删掉了。

## 第14课：排行榜是一道算术题

两篇论文有这些评分：

|论文|评分|人数|平均分|
|---|---|---|---|
|A|5、3|2|(5+3)÷2 = 4|
|B|5|1|5÷1 = 5|

如果只按平均分，B更高；但只有一个人评分可能不够参考。因此页面 `Paper rankings` 默认要求至少2份评分。B暂时不出现。你能把最低人数改成1，也能选择出版年份。

从零实现：

1. 在 `reviews` 表按 `paper_id` 分组。想象把同一篇论文的评分放同一个碗里。
2. 每碗算 `AVG(rating)`（平均分）和 `COUNT(*)`（人数）。
3. 只留下人数达到要求的碗，连上论文标题。
4. 先按平均分从高到低，再按人数、论文编号决定并列顺序。
5. 每页只取一部分，避免一次搬出所有结果。

真实代码在 `community.py` 的 `leaderboard`。先把评分算好再连接论文，避免连接作者或点赞时把同一份评分重复计入。这是面试中能讲清楚的一个 SQL 设计选择。

试一试：甲乙分别给同一篇论文5分和3分；排行榜应显示4分、2份评分。全新网站没有人评分，排行榜是空的，这是正确行为。这里的平均分是小型演示数据，不代表学术影响力或真实论文质量。

小题：A有5、3、1三份评分，平均分是多少？答案：9÷3=3。给其中一条评论点赞不会改变论文平均分。

## 第15课：合作者图像同桌关系图

假设一篇论文由小红、小明共同完成。画两个圆，连一条线，就表示他们合作过。另一篇又合作，还是同一条关系，但合作篇数变成2。

1. 打开一个作者页面，点 `Explore coauthor network`。
2. 中间是当前作者，周围是和这个作者共同写过论文的人。
3. 圆和线下面还有表格。同一份数据也能直接读文字，不必只看图。
4. 点另一个作者，换这个人为中心再看。

从零实现：先在 `paper_authors` 找当前作者参加的论文，再在同一张表找这些论文的其他作者。这叫“自连接”：给同一本登记册起两个别名，一份用来找论文，另一份用来找伙伴。排除作者自己，按伙伴编号分组，用 `COUNT(DISTINCT paper_id)` 数不同论文。

代码在 `community.py` 的 `network`，网页在 [`network.html`](../../navigator/templates/network.html)。SVG 是浏览器认识的一种画图文字：`circle` 画圆，`line` 画线，`text` 写字。Python 算好圆的位置，Jinja 填进去。

最多显示24位直接合作者，超过会提示有截断。没有展开“朋友的朋友”，也没有计算中心性等图算法。作者和论文都是虚构样例。面试时应称它为“基于关系表自连接的直接合作者可视化”。

小题：A和B合作过，B和C合作过，但A和C没有共同论文。以A为中心，C会出现吗？答案：不会，只看直接合作。

## 给已经装过旧版项目的人：先给登记册加新页

更新代码不会自动更新已有 MySQL 表。数据库迁移就是“保留旧内容，给登记册加新栏目”。

在项目根目录、已激活虚拟环境的终端执行：

```bash
flask --app navigator migrate-db
```

Docker 用户执行：

```bash
docker compose build app
docker compose run --rm app flask --app navigator migrate-db
docker compose up -d app
```

预期看到 `Community schema ready; existing lists remain private.`。它增加3张点赞表和公开开关，可以重复运行，旧书单仍然私人。新建空数据库直接用完整 `schema.sql`，总共15张表。不要为升级删除数据库或重新运行清空操作。

完成后去[第16课](10_PUBLIC_DEPLOYMENT.md)，让别人通过公开网址访问。
